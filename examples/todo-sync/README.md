# Todo: che-rest + che-tauri

Небольшой пример синхронизации протокола 2: сервер с SQLite и два независимых
Tauri-клиента. Можно создавать задачи, менять название и отметку выполнения,
удалять их, работать без сервера и разрешать конфликты. Синхронизация запускается
кнопкой. Интерфейс — обычные HTML/CSS/JS; Node.js, npm и Vite для запуска не нужны.

## Запуск

Нужны Rust и системные зависимости Tauri 2 для вашей платформы
(на Linux — GTK 3, WebKitGTK 4.1 и инструменты сборки). Все команды ниже выполняются
из `che-tauri/examples/todo-sync`. Пример использует соседние исходники
`che-orm`, `che-rest` и `che-tauri`.

Сервер, первый терминал:

```bash
cargo run -p todo-sync-server -- migrate
cargo run -p todo-sync-server -- serve
```

API слушает `http://127.0.0.1:3007/api/todos/`. База — `server.sqlite`.
Для демонстрации используется один пользователь с доступом ко всем задачам
и известный токен `todo-demo-token`. Сервер слушает только loopback.

Клиент A, второй терминал:

```bash
TODO_CLIENT_DB=client-a.sqlite cargo run -p todo-sync-client --no-default-features --bin todo-client-db -- migrate
TODO_CLIENT_DB=client-a.sqlite cargo run -p todo-sync-client --bin todo-sync-client
```

Клиент B, третий терминал:

```bash
TODO_CLIENT_DB=client-b.sqlite cargo run -p todo-sync-client --no-default-features --bin todo-client-db -- migrate
TODO_CLIENT_DB=client-b.sqlite cargo run -p todo-sync-client --bin todo-sync-client
```

На Windows задайте `TODO_CLIENT_DB` средствами своей оболочки, например
`$env:TODO_CLIENT_DB="client-a.sqlite"` в PowerShell, затем выполните команды Cargo.
Два клиента должны использовать **разные файлы** SQLite. Открытие клиента не
требует сети. Миграции применяются только отдельной командой `migrate`; повторный
запуск безопасен и сохраняет существующие данные. Истории в `initial.rs` уже
зафиксированы, их не нужно генерировать при запуске.

Это отдельный Cargo workspace: проверки из корня библиотеки `che-tauri` его
не запускают. `Cargo.lock` фиксирует зависимости приложения. Прямой `cargo run`
использует локальные файлы интерфейса из `client/ui`; установка Tauri CLI не нужна.

## Что попробовать

1. Создайте задачу в A и нажмите «Синхронизировать». Синхронизируйте B — задача
   появится там.
2. Остановите сервер (`Ctrl+C`), создайте или измените задачи в A. Закройте и
   снова откройте A: изменения останутся в SQLite. Верните сервер и нажмите
   кнопку синхронизации.
3. На одной задаче поменяйте название в A и отметку выполнения в B до
   синхронизации. Синхронизируйте A, B, затем A: оба изменения сохранятся.
4. Поменяйте одно название по-разному в A и B. Синхронизируйте A, затем B.
   В B появятся обе версии с выбором «Оставить мою» / «Принять серверную».
   Выберите версию и синхронизируйте оба клиента.
5. Удалите задачу в A и синхронизируйте A, затем B.

## Устройство

- `model`: UUID-модель `Todo` и ORM-сериализатор, общий для сервера и HTTP-маппинга.
- `server`: обычный ViewSet с `IsAuthenticated` и `ModelSyncEndpoints`.
  Записи идут через POST/PATCH/DELETE, загрузка — через `/todos/sync/changes/`.
- `client/src-tauri`: клиентская схема через `ModuleContext::sync_model`,
  `TauriSync`, HTTP-транспорт из `che-rest` и четыре UUID CRUD-команды.
- `client/ui`: локальный список и отправка `che_model_sync`. Число шагов одного
  нажатия ограничено; конфликты останавливают цикл и показываются пользователю.

Клиентские CRUD-команды используют настроенный sync-клиент; кеш удалённых
ресурсов здесь не участвует. HTTP остаётся в `che-rest`, outbox/merge/курсоры —
в `che-sync`, UI и invoke — в `che-tauri`.

`TodoSerializer` в общем крейте — ORM-сериализатор для серверного ViewSet и
`RestResource`. Он отличается от `che_tauri::ModelSerializer`, описывающего
обычные invoke-ресурсы с i64 ID. В этом примере UUID CRUD-команды принадлежат
приложению. Их имена и `che_tauri::che_model_sync` зарегистрированы в одном
`tauri::generate_handler!`; полный путь нужен для макросов внешнего крейта.

## Настройки

| Переменная | Где используется | Значение по умолчанию |
| --- | --- | --- |
| `TODO_SERVER_DB` | Сервер и его миграции | `server.sqlite` |
| `TODO_CLIENT_DB` | Клиент и его миграции | `client-a.sqlite` |
| `TODO_SYNC_URL` | Клиентский HTTP-транспорт | `http://127.0.0.1:3007/api` |
| `TODO_SYNC_TOKEN` | Сервер и клиент | `todo-demo-token` |

Пути к SQLite разрешаются относительно текущего рабочего каталога. Используйте
тот же путь для команды миграции и запуска соответствующего приложения.
Токен клиента должен совпадать с серверным; UI не выполняет login и не меняет
учётную запись. Один клиентский файл принадлежит одной паре сервер/аккаунт.
Для другого сервера используйте новый файл и примените клиентские миграции;
ожидающие отправки запросы нельзя перенаправлять в другую серверную историю.

## Если что-то не запускается

- Ошибка открытия sync-клиента: проверьте, что выполнен `todo-client-db migrate`
  с тем же `TODO_CLIENT_DB` и из того же каталога.
- Сервер сообщает об отсутствующей таблице: выполните серверную команду `migrate`
  с тем же `TODO_SERVER_DB`.
- Синхронизация возвращает ошибку подключения или авторизации: проверьте работающий
  сервер, `TODO_SYNC_URL` и токен. Локальные записи и ожидающие запросы сохраняются;
  после восстановления подключения нажмите кнопку ещё раз.
- Конфликт: выберите версию в UI и повторите синхронизацию. Цикл сам останавливается
  при конфликте и ограничен 30 шагами, чтобы не зациклиться на зависимостях.
- Ошибка сборки GTK/WebKitGTK: нужны системные зависимости desktop Tauri;
  флаг `--no-default-features` исключает desktop-бинарник примера, но библиотека
  `che-tauri` всё ещё зависит от Tauri и может требовать системные библиотеки.

## Проверка

```bash
cargo check --workspace
cargo build --workspace
cargo test -p todo-sync-server -p todo-sync-client --no-default-features
cargo clippy --workspace --all-targets --no-deps -- -D warnings
cargo fmt --all --check
```

Для проверки синтаксиса UI при наличии Node.js:

```bash
node --check client/ui/app.js
```

Тест `two_clients` открывает временные файловые SQLite-базы и настоящий HTTP-сервер
на свободном loopback-порту. Он проверяет повторные миграции, офлайн-изменения и
перезапуск, два устройства, автоматическое слияние, выбор версии конфликта,
удаление и отказ с неверным токеном. Рабочие базы примера он не использует.
`cargo check` и `cargo build` с обычными features проверяют также desktop-бинарник,
Tauri-контекст, иконку и регистрацию invoke-команд. Они не открывают окно и не
проверяют UI вручную — для этого пройдите сценарии выше с двумя клиентами.
